# Module 2 Phase A: Provider Abstraction + Chat Completions Migration

⚠️ **Medium** — Architectural refactor with multiple service replacements and a database schema change. Each individual task is straightforward, but the migration from managed threads to self-managed messages touches several files.

## Goal

Transition from OpenAI's managed Assistants/Responses API to the standard **Chat Completions API** with a multi-provider abstraction layer. This enables support for any OpenAI-compatible endpoint: OpenAI, OpenRouter, Ollama, LM Studio, or any custom provider.

**This follows Option A (Replace)** — the Responses API code is fully removed. Messages are stored in Supabase instead of OpenAI threads.

## Proposed Changes

### 1. Database — New `chat_messages` Table

Create a `chat_messages` table with RLS to store messages ourselves (previously managed by OpenAI threads). Drop the `thread_id` column from `user_threads`.

```sql
create table public.chat_messages (
    id uuid default gen_random_uuid() primary key,
    thread_id uuid not null references public.user_threads(id) on delete cascade,
    role text not null check (role in ('system', 'user', 'assistant')),
    content text not null,
    model text,
    provider text,
    created_at timestamptz default now()
);

alter table public.chat_messages enable row level security;
create policy "Users can view own messages" on public.chat_messages for select
    using (thread_id in (select id from public.user_threads where user_id = auth.uid()));
create policy "Users can insert own messages" on public.chat_messages for insert
    with check (thread_id in (select id from public.user_threads where user_id = auth.uid()));

create index idx_chat_messages_thread on public.chat_messages(thread_id, created_at);

alter table public.user_threads drop column if exists thread_id;
```

**Validation:** Query `chat_messages` table structure and RLS policies via Supabase dashboard.

### 3. Backend — Completions Service (`services/completions_service.py`) [NEW]

Replaces `openai_service.py`. Uses the standard OpenAI Python SDK with `base_url` override to work with any compatible provider.

- `_get_client()` — Lazy-init OpenAI client using provider config
- `chat_stream(messages, model=None)` — Stream chat completions, yield content deltas
- `generate_title(user_message)` — Generate thread title using the title model

**Validation:** Send a test message and verify streaming works.

### 4. Backend — Message Service (`services/message_service.py`) [NEW]

CRUD for chat messages stored in Supabase.

- `get_messages(thread_id)` — Fetch all messages for a thread, ordered by `created_at`
- `save_message(thread_id, role, content, model=None, provider=None)` — Insert a message
- `build_completion_messages(thread_id, system_prompt)` — Build the `messages` array for chat completions: `[system_prompt] + [all thread messages in order]`

**Validation:** Insert and retrieve messages via the service functions.

## Architecture

```
.env (LLM_PROVIDER, LLM_BASE_URL, LLM_API_KEY, LLM_MODEL)
  ↓
provider_config.py (read env → resolve defaults → return config)
  ↓
completions_service.py (OpenAI SDK with base_url override)
  ↓
/v1/chat/completions → OpenAI | OpenRouter | Ollama | LM Studio | Custom

message_service.py ←→ Supabase: chat_messages table (RLS-protected)

chat.py router: save msg → build messages → stream completions → save response
threads.py router: CRUD threads + messages (no OpenAI dependency)
```
